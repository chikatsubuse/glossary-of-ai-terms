# AI用語マップ

AI領域の主要用語を1用語1カード（1 Markdownファイル）で整理するプロジェクト。

## ディレクトリ構成（案）

カード生成の開始時に、カテゴリごとのフォルダを作成する。

```
ai-terms/
├── README.md            … このファイル（テンプレ・ルール・進行状況）
├── 00-term-list.md      … 用語リスト（カテゴリ・依存順）
├── 00-model-table.md    … モデル一覧（各社の現行モデル早見表）
├── 01-basics/           … 基礎
├── 02-models/           … モデルの仕組みと種類
├── 03-training/         … モデルの学習
├── 04-usage/            … 活用の基礎
├── 05-agents/           … AIエージェント
├── 06-risk-governance/  … リスク・評価・ガバナンス
├── 07-infrastructure/   … インフラ
├── 08-interfaces/       … インターフェース・開発形態
├── 09-labs-models/      … プレイヤー：AIラボと主力モデル
├── 10-tools-products/   … プレイヤー：開発ツール・エージェント製品
└── 11-platforms/        … プレイヤー：インフラ・プラットフォーム
```

- ファイル名は英語kebab-case（例: `pre-training.md`, `rag.md`, `claude.md`）
- カテゴリの並び＝依存順。カードの中では、それより前のカテゴリの用語を説明なしで使ってよい（再定義しない）

## カードテンプレート

### 概念用

```
# 用語名（English）

- 用語名＝〜（一行定義）
- 仕組み・代表手法（必要ならサブ項目で一段だけ深掘り）
- 実務への含意（なぜビジネス側が知るべきか）
- 課題・最新動向
```

### プレイヤー用（企業・プロダクト）

```
# 企業・プロダクト名

- 〜＝何者か（一行）
- 代表プロダクト・モデル
- 業界内のポジション・特徴
- 最近の動き（時点を明記）
```

## 文体・表記ルール

- 常体・体言止め。1項目1行、1カード4〜6行
- 見出しは日英併記
  - 日本語が定着している用語 → 日本語（English）：例「事前学習（Pre-training）」
  - 英語・略語が定着している用語 → 英語（正式名称）：例「RAG（Retrieval-Augmented Generation）」
  - 定着した日本語訳がない用語に無理な直訳は当てない
- 英語・略語の補足は初出のみ括弧書き
- 数字・固有名詞は具体的に書く
- エージェント等のシステムの定義は擬人化せず、動作の記述で書く（擬人的な見え方に触れるときは「〜ように見える」と明示する）
- 依存順の例外：固有名詞（企業・製品・モデル名）と、一般に通用する語（AI・生成AI・アプリ・クラウド・エージェント・プロンプト・GPU・API等）は、定義カテゴリより前でも使用可
- 英語が定着し日本語の定訳もある語は「英語（日本語訳）」の併記も可（例：Attention（注意機構））
- 変化しやすい事実（シェア、性能比較、企業動向）には「2026年8月時点」と明記

## 基準サンプル

以下の2枚の深さ・文体に全カードを合わせる。

### トークン（Token）

- トークン＝LLMが文章を読み書きする最小単位。単語より一段細かい文字列の断片（サブワード）
- トークナイザが文章をトークン列に変換してからモデルに入力する
  - 分割ルールは学習データでの出現頻度から決まり、頻出する文字列ほど1トークンにまとまる（標準手法はBPE）
- API料金も、コンテキストウィンドウ（一度に扱える量の上限・後述）の残量も、文字数ではなくトークン数で数える
  - 同じ内容でも日本語は英語の1.5〜2倍前後のトークンを消費しやすく、費用と入力上限の両方に効く（token tax）
- 日本語語彙の拡張やトークナイザ不要のアーキテクチャなど、言語間の効率差を縮める研究が進行中

### RAG（Retrieval-Augmented Generation）

- RAG＝質問に関連する文書を検索し、プロンプトに添えて回答させる手法
- 典型構成は「文書をベクトル化してベクトルDBに格納 → 質問と意味が近い文書を検索して渡す」
  - モデル自体は再学習せず、その場で渡す情報だけで知識を補う
- 学習データにない社内情報・最新情報を扱える一方、検索の精度がそのまま回答品質の上限になる
- コンテキストウィンドウの長大化や、エージェント自身が検索するAgentic RAGの登場で、典型構成は変化しつつある

## 更新・メンテナンス

- **09〜11（プレイヤー系）の更新時は、必ずWeb検索で最新事実を確認してから書き換える**（モデルの版数・資金調達・評価額・提携・訴訟）。AIの学習知識だけで書かない——初版作成時も「SpaceXAI」など知識カットオフ後の変化が複数見つかった
  - AIに更新させる場合は「調査（系列ごとに分担してファクト収集）→執筆」の2段構えを推奨。初版は5〜6系列の並列Web調査で作成（2026年8月）
- **00-model-table.md（モデル一覧）はリポジトリ内で最も揮発性が高い**。プレイヤー系と同じ扱い（Web検索必須）で現行世代へ入れ替え、冒頭の時点表記も更新する
- 更新頻度の目安：プレイヤー系・モデル一覧は四半期に1回。概念系（01〜08）は最終行の「課題・最新動向」のみ半年〜1年に1回
- 更新時は本文の「◯年◯月時点」の時点表記も必ず更新する
- 同じ事実が複数カードに登場することがある（例：オープンウェイトの勢力図、Microsoft×OpenAIの関係、SpaceX関連）。1枚を直したら関連語でgrepして横展開する
- 大きく手を入れたときは通しレビューを再実施する（事実の矛盾・依存順と表記ゆれ・文体と時点表記の3観点＋ファイル数と見出しの機械チェック）
